# Codex Master Prompt — EddaStore Admin Completion

أنت تعمل على مشروع EddaStore القائم. المطلوب إغلاق مرحلة Admin Area بالكامل قبل البدء في Store pages.

## اقرأ المراجع أولًا وبالترتيب
1. `docs/EDDASTORE_BRAND_KIT.md`
2. `docs/ADMIN_UI_UX_STANDARD.md`
3. `docs/ADMIN_ARCHITECTURE_GUIDE.md`

## مهمتك

افحص المشروع الحقيقي ثم نفّذ التعديلات على الملفات نفسها. لا تكتفِ بخطة أو توصيات. أكمل كل ما يخص `Areas/Admin` وDashboard ووحدات الإدارة الموجودة في المشروع، مع واجهة احترافية عالية الجودة ومتسقة مع Brand Kit.

### UI/UX — مطلب أساسي وليس تجميليًا
- الواجهة الإدارية الحالية ليست مرجعًا بصريًا ملزمًا؛ يمكن إعادة تصميم Admin Layout وCSS الإداري إذا كانت النتيجة الحالية لا تحقق المعايير.
- Brand Kit هو المرجع البصري الأعلى. اتبع الألوان والخطوط والشخصية المحددة في `EDDASTORE_BRAND_KIT.md`.
- طبّق `ADMIN_UI_UX_STANDARD.md` على الـ Sidebar والـ Topbar والـ Dashboard والجداول والنماذج والتنبيهات وحالات الفراغ والأخطاء والـ responsive behavior.
- لا تنشئ شكلًا مختلفًا لكل وحدة. ابنِ Design Tokens ومكونات متناسقة، ثم طبّقها على كل صفحات Admin.
- حافظ على العربية وRTL، مع دعم عرض أسماء المنتجات والموديلات الإنجليزية بشكل صحيح.
- لا تستخدم Tailwind CDN أو Bootstrap إضافيًا أو مكتبات جديدة قبل فحص الموجود. لا تضف dependency لمجرد التزيين.
- لا تغيّر Store layout أو Store pages في هذه المرحلة. أي تعديل خارج Admin يجب أن يكون ضروريًا ومحدودًا ومبررًا.
- لا تعتبر UI مكتملًا لمجرد نجاح build؛ راجع التناسق، responsive layout، حالات empty/error/success، accessibility، وروابط التنقل.

### المعمارية
- حافظ على Generic Repository Pattern الحالي. اقرأ الـ interfaces والـ implementations والخدمات قبل التعديل.
- Controllers تستخدم Services، والخدمات تستخدم Repositories وفق النمط الموجود. لا تنقل منطق الأعمال إلى Controller أو View ولا تكرر وظائف Generic Repository بلا داعٍ.
- لا تخترع أسماء properties أو DbSets أو methods؛ افحص المصدر.
- التزم بالـ soft delete وIdentity والصلاحيات وAnti-Forgery والـ validation الموجودين.

### النطاق
افحص كل الكيانات الموجودة فعلًا، وقرّر العملية المناسبة لكل منها:
- Dashboard وإحصاءاته وروابطه.
- Products وصورها وأسعارها ومخزونها.
- Categories والتصنيفات الفرعية.
- Brands وشعاراتها.
- Orders وعناصر الطلب وتاريخه.
- Customers/Users والأدوار.
- Coupons.
- Payments.
- Shipments/Shipping.
- Invoices.
- Reviews وأي كيانات أخرى موجودة.

القائمة للفحص وليست أمرًا بإنشاء حذف/تعديل عشوائي لكل جدول. كيانات الطلبات والمدفوعات والشحن والفواتير تحتاج workflows آمنة، وليس CRUD يكسر سلامة السجلات. لا تنفذ مدفوعات أو استردادات حقيقية.

### لكل وحدة مناسبة
- Controller، ViewModels، Views اللازمة، validation server-side.
- Index مع البحث والفلاتر والـ pagination حيث يلزم، مع حفظ الفلاتر أثناء التنقل.
- Create/Edit/Details حسب احتياج الكيان.
- رسائل عربية واضحة وحالات empty/error/success.
- روابط تنقل تعمل فعلًا، ولا أزرار شكلية أو TODOs.
- صلاحيات حسب نظام المشروع؛ كل تعديل بيانات POST محمي بـ Anti-Forgery.
- رفع ملفات آمن وفق Architecture Guide.

### طريقة التنفيذ
1. افحص الملفات الفعلية وسجّل الوحدات الناقصة.
2. أصلح الـ Admin shell وDesign Tokens أولًا وفق Brand Kit.
3. ابنِ نمطًا مرجعيًا للجداول ونمطًا للنماذج والتنبيهات، ثم وحّد جميع الوحدات.
4. أكمل Products ثم Categories وBrands ثم باقي وحدات الإدارة المناسبة.
5. أكمل Dashboard والروابط والصلاحيات وحالات الواجهة.
6. شغّل `dotnet restore` و`dotnet build` والاختبارات المتاحة. أصلح أخطاء التغييرات.
7. راجع كل المسارات والـ views والـ DI يدويًا.

لا تتوقف بعد أول وحدة ولا تنتظر مني موافقة بعد كل ملف. اتخذ القرارات الآمنة المتسقة مع المشروع، واسأل فقط عند وجود مانع حقيقي لا يمكن حله من الكود.

## التسليم النهائي
قدّم تقريرًا بالعربية يشمل:
- الوحدات التي اكتملت وما الذي بقي.
- أهم الملفات التي أُنشئت أو عُدلت.
- نتيجة build والاختبارات بدقة.
- أي قيود أو قرارات تحتاج مراجعة.
- تأكيد أن Store pages لم يتم البدء فيها.

لا تدّعِ أن الاختبارات نجحت إذا لم يتم تشغيلها.
