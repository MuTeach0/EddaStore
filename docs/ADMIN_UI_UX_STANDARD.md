# EddaStore Admin — UI/UX Standard

هذه قواعد تنفيذية إلزامية لكل صفحات لوحة الإدارة. المطلوب تجربة منتج متماسكة ومصقولة، وليست مجرد تغيير ألوان.

## 1. UX principles

- وضوح التسلسل البصري: عنوان الصفحة ثم وصف قصير عند الحاجة، ثم الإجراء الرئيسي، ثم أدوات العمل والبيانات.
- كل صفحة يجب أن تجيب بسرعة: أين أنا؟ ما البيانات؟ ما الإجراء الأساسي؟ ما حالة العملية؟
- اجعل المهام المتكررة قصيرة، وقلّل النقرات غير الضرورية.
- استخدم تسميات عربية مباشرة ومتسقة. تجنب النصوص الطويلة داخل الأزرار.
- لا تعرض بطاقات إحصائية أو رسومًا شكلية بلا معنى أو بيانات حقيقية.
- لا تستخدم عناصر UI غير تفاعلية تبدو كأزرار، ولا تترك أزرارًا بلا تنفيذ.
- حافظ على البيانات المدخلة عند فشل التحقق، وأظهر الخطأ بجوار الحقل وملخصًا واضحًا أعلى النموذج.
- إجراءات الحذف أو الإلغاء الخطرة تحتاج تأكيدًا واضحًا، مع حماية الخادم دائمًا.
- كل شاشة تدعم loading/error/empty/success states عندما ينطبق ذلك.

## 2. Admin shell

أنشئ أو حسّن Admin shell ليشعر المستخدم بأنه جزء من EddaStore:
- Sidebar واضح وثابت على الشاشات الكبيرة، قابل للطي أو التحول إلى drawer على الموبايل.
- في RTL يكون التنقل الجانبي في اليمين ما لم تمنع البنية الحالية ذلك لسبب موثق.
- يوضح الرابط النشط الصفحة الحالية بصريًا وبإمكانية وصول مناسبة.
- مجموعات تنقل منطقية مثل: الرئيسية، الكتالوج، المبيعات، العملاء، التسويق، الإعدادات؛ لا تعرض إلا الوحدات المنفذة فعلًا.
- Topbar مختصر يتضمن عنوان الصفحة/مسار التنقل عند الحاجة، وحساب المستخدم والإجراءات العامة الموجودة فعليًا.
- محتوى الصفحة لا يلتصق بحواف الشاشة ولا يترك مساحات مهدرة.
- على الموبايل يجب أن تظل الجداول والنماذج قابلة للاستخدام، وليس فقط مصغرة بصريًا.

## 3. Dashboard

- تحية/عنوان مختصر ومحدد، مع فترة البيانات إن كانت الإحصاءات زمنية.
- بطاقات KPI قليلة ومفيدة، مع label واضح ورقم قابل للمسح السريع ووصف أو مقارنة فقط إذا كانت محسوبة فعليًا.
- اختصارات لأكثر مهام الإدارة استخدامًا، مثل إضافة منتج وعرض الطلبات، إذا كانت المسارات موجودة.
- عرض آخر الطلبات أو تنبيهات المخزون فقط إذا كان مصدر البيانات موجودًا ويمكن استعلامه بشكل صحيح.
- لا تخترع أرقامًا ولا تضع بيانات تجريبية في الإنتاج.
- لا تحوّل Dashboard إلى شبكة ضخمة من البطاقات؛ حافظ على أولوية البيانات الفعلية.

## 4. Lists and tables

كل Index/List يجب أن يوفر عند الحاجة:
- عنوانًا واضحًا وإجراءً رئيسيًا واحدًا.
- بحثًا وفلاتر ذات صلة فقط، مع زر مسح/إعادة ضبط واضح.
- عدد النتائج أو وصفًا لحالة القائمة إذا توفر من المصدر.
- جدولًا منظمًا بعناوين أعمدة مفهومة، ومحاذاة مناسبة للأرقام والأسعار والتواريخ.
- حالة فارغة تشرح عدم وجود نتائج وتوفر إجراءً مناسبًا عند الإمكان.
- Pagination صحيحة تحافظ على search/filter/sort state.
- إجراءات الصف مجمعة وغير مزدحمة؛ لا تجعل الحذف الإجراء الأكثر بروزًا.
- على الشاشات الصغيرة: تمرير أفقي مضبوط أو عرض بطاقات مناسب، دون كسر الصفحة.
- لا تستخدم ألوانًا قوية لكل صف أو كل badge.

## 5. Forms

- قسّم النماذج الطويلة إلى أقسام مفهومة.
- Labels ثابتة وواضحة، والـ placeholders أمثلة قصيرة وليست بديلًا للـ label.
- وضّح الحقول المطلوبة، حدود الإدخال، وحدات القياس، العملة، وتنسيق الأرقام عند الحاجة.
- اعرض Validation summary ورسالة بجانب الحقل؛ انقل التركيز منطقيًا إلى أول خطأ إن أمكن.
- أزرار Save وCancel واضحة ومتسقة، وتجنب فقدان البيانات بسبب التنقل غير المقصود.
- في Edit، وضّح الفرق بين البيانات الحالية والتغييرات الجديدة.
- للصور: معاينة فعلية، حالة عدم وجود صورة، قيود النوع والحجم، وتحديد الصورة الرئيسية إذا كان النظام يدعم ذلك.

## 6. Status, feedback and accessibility

- النجاح والخطأ والتحذير لها نمط ثابت، ونص يشرح النتيجة.
- لا تعتمد على اللون وحده؛ استخدم النص والأيقونة عند توفرها.
- استخدم semantic HTML، labels مرتبطة بالحقول، focus states واضحة، وتباينًا مقروءًا.
- احترم keyboard navigation وprefers-reduced-motion.
- الأزرار لها حالات hover/focus/disabled، مع منع double submit حيث يلزم.
- تأكد من ظهور رسائل `TempData` وعدم تكرارها في الـ Layout والصفحة.
- استخدم أسماء accessible للأيقونات التي لا يصاحبها نص.

## 7. Responsive and visual polish

- راجع عمليًا على desktop/tablet/mobile widths.
- لا تستخدم `position: absolute` لتخطيط المحتوى الأساسي.
- حافظ على scale ثابتة للمسافات، أحجام الخطوط، radius، الظلال، ارتفاع الحقول والأزرار.
- استخرج Design Tokens إلى CSS variables مركزية في `admin.css` أو الملف المناسب.
- أعد استخدام مكونات/partials مشتركة للتنبيهات، pagination، badges، وحالات empty/loading إذا كان ذلك يقلل التكرار دون تعقيد.
- تجنب inline styles المتكررة وCSS المتضارب.

## 8. طريقة العمل البصرية الإلزامية

1. افحص كل ملفات الـ Brand Kit وCSS والـ Layout الحالي.
2. سجّل نقاط الألم المرئية في Admin الحالي.
3. حدّث Admin shell وDesign Tokens أولًا.
4. أنشئ نمطًا مرجعيًا واحدًا لصفحة Index ونمطًا واحدًا للنموذج، ثم طبقه على كل الوحدات.
5. بعد كل دفعة، افحص عدم وجود layout breaks، تضارب CSS، أو اختلاف غير مبرر بين الوحدات.
6. لا تعتبر المهمة منتهية لمجرد أن الكود يبني؛ راجع تجربة الاستخدام واتساق الصفحات.

## 9. حدود التغيير

- مسموح إعادة تصميم واجهات `Areas/Admin` وملفات CSS الخاصة بها بما يتوافق مع Brand Kit.
- ممنوع تغيير هوية العلامة أو بناء هوية بصرية جديدة من الصفر.
- ممنوع تغيير صفحات Store في هذه المرحلة.
- ممنوع تغيير Generic Repository Pattern أو خلط منطق البيانات داخل Views/Controllers.
